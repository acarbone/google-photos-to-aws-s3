# Research: Google Photos (Takeout) → AWS S3 Backup Tool

## 1. Context

Repo is currently an empty Spec-Driven scaffold (no application code — see `git log`: single "Initial commit" of the template itself). This is a **greenfield Tier 2 feature**: there is no existing codebase pattern to reconcile with, so this research focuses on the two external systems the tool bridges (Google Takeout export format, AWS S3 upload/storage mechanics) rather than on internal code archaeology.

Business goal (user-stated): free up Google Account storage by moving the photo/video library to low-cost AWS S3, without executing any destructive action against Google Photos itself. The user will export their library via Google Takeout themselves; this tool's job starts at the exported `.zip` files.

## 2. Google Takeout — Google Photos export format

Sources: mattwilson1024/google-photos-exif (GitHub), metadatafixer.com, tonfotos.com Takeout guides (see chat citations).

- A Takeout export for a large photo library is delivered as **multiple numbered `.zip` files** (e.g. `takeout-20260101T000000Z-001.zip`, `-002.zip`, …), each capped around a user-chosen size (commonly up to 50GB/part). A tool that assumes "one zip" will break on any non-trivial library — **must support N zip parts as input**, discovered from a directory or explicit file list.
- Inside each zip: `Takeout/Google Photos/<Album or date folder>/<file>`. Folders are a mix of **named albums** and **year/date-based buckets** for photos not in any album. The **same photo can appear in multiple folders** (once per album it belongs to) — Takeout does not dedupe. This directly informs the need for content-hash dedup (§4 below), which materially reduces S3 spend since the same bytes are otherwise billed once per album membership.
- Every media file has a **JSON sidecar** carrying metadata Google strips from the file itself: `photoTakenTime`, GPS coordinates, description, favorited flag, people/face tags, upload device. **Naming has changed over time and is not consistent**: pre–late-2024 exports used `<filename>.json` (e.g. `IMG_1234.jpg.json`); Google silently renamed the pattern to `<filename>.supplemental-metadata.json` in late 2024. **An export requested today can contain either or both patterns** depending on when the underlying items were uploaded to Google. The tool must probe for both suffixes when pairing a media file to its sidecar, and must not hard-fail if a sidecar is missing (some items legitimately have none).
- Known edge cases from the community tooling ecosystem (mattwilson1024/google-photos-exif exists specifically to work around these): filenames truncated by Google's own export process when they exceed ~46–51 characters, meaning the media filename and the JSON's embedded "title" field can diverge from the sidecar's own filename-derived name; numbered-duplicate suffixes (`IMG_1234(1).jpg` next to `IMG_1234(1).json` vs `IMG_1234.jpg(1).json` — the counter position is inconsistent between the two). **Design consequence**: pairing must primarily walk zip entries by directory proximity + longest-common-prefix matching, not by naive string concatenation, and must degrade gracefully (media file with no sidecar ⇒ upload with no extended metadata, logged, never a hard error).

**Conclusion**: treat the JSON sidecar as best-effort enrichment, never a correctness dependency for the backup itself. The photo/video bytes are always backed up; metadata is attached when found.

## 3. AWS S3 — storage class and upload mechanics

Sources: AWS S3 storage-class docs, boto3 `TransferConfig` docs (see chat citations).

- User selected **S3 Glacier Instant Retrieval** (`GLACIER_IR` storage class constant) as the default: lower steady-state cost than Standard-IA, and — unlike Glacier Flexible Retrieval / Deep Archive — objects remain **immediately readable** (millisecond retrieval, same as Standard) at read-access cost, no restore job needed. This is the right fit for personal photo backups the user may occasionally want to view without planning a retrieval job days in advance. Minimum storage duration charge (90 days) and a per-request retrieval fee apply — acceptable trade-offs for this use case and worth surfacing to the user in docs, not hidden.
- Multiple sources reiterate the common AWS-recommended pattern is *land in S3 Standard, let a lifecycle rule transition objects* rather than writing directly at a cold class. That pattern optimizes for *unknown* access patterns on freshly created data. It does not apply here: the data is a one-time historical backup with a known, immediate "infrequently accessed" profile (photos leaving Google specifically to sit cheaply). **Decision**: upload directly at `GLACIER_IR` (per explicit user choice), skip the lifecycle-transition indirection — it would only add a delay before reaching the cost point the user already asked for. Document the trade-off in README so users with different access patterns know they can override the storage class.
- `boto3`'s managed transfer (`upload_fileobj` / `TransferManager`) handles multipart upload transparently once a file exceeds `multipart_threshold` in a `TransferConfig` (commonly set ~25MB — reasonable default for this tool given many phone videos exceed that). It accepts non-seekable file-like objects (a `zipfile.ZipExtFile` stream, or better a `SpooledTemporaryFile` we control) and manages part upload/retry itself. **Important idempotency detail**: a multipart upload is not materialized as a readable S3 object until `CompleteMultipartUpload` succeeds — a process killed mid-upload leaves *no visible object*, only an orphaned incomplete-multipart-upload record that continues to incur storage cost until aborted. **Design consequence**: the S3 bucket must be created (or the user instructed to configure) with an `AbortIncompleteMultipartUpload` lifecycle rule (e.g. 7 days), and the tool's own state machine must treat "object not found via HEAD" as the sole truth for "not yet uploaded," never trusting an in-memory or crash-torn local state alone.
- botocore's built-in retry (`retries={"mode": "adaptive", "max_attempts": N}`) handles throttling/network-blip retries at the request level; the tool adds one more layer above it — a **per-file** status machine — to survive whole-process kills (Ctrl+C, laptop sleep, crash), which botocore's request-level retry cannot do anything about.

## 4. Idempotency & resumability pattern

This is a long-running, interruption-prone process (hundreds of GB, possibly running over many hours across multiple sessions on a personal laptop). Requirements distilled from the user's own framing ("manage the state, idempotency… by recovering the execution, the script restores from where it left, without restarting from scratch"):

- **External memory, not in-process state**: a local SQLite database (not JSON — needed for safe partial writes and query-by-status at library scale of 10⁴–10⁵+ files) recording one row per discovered media file: stable id, source zip + entry path, size, sha256, status (`pending`/`uploading`/`uploaded`/`skipped_duplicate`/`failed`), s3 key, s3 ETag, error, timestamps.
- **Discovery is idempotent by construction**: re-scanning the same Takeout zips uses `INSERT OR IGNORE` keyed on a stable id (hash of zip filename + entry path) — running discovery twice, or adding more zip parts later, never creates duplicate rows.
- **Upload is idempotent by verification, not by trust**: before uploading, HEAD the target S3 key; if it already exists with a matching stored `sha256` in its object metadata, mark `uploaded` and skip re-transferring the bytes. This makes the *S3 bucket itself* the ultimate source of truth that survives even a fully-deleted local state DB (degraded but safe: worst case is redundant HEAD calls, never a duplicate paid upload of the same content, at the cost of one full re-hash pass through the zips).
- **Crash-safe status transitions**: rows are committed to `uploading` immediately before a transfer starts and to `uploaded`/`failed` immediately after — never batched — so a killed process leaves at most one row stuck in `uploading`. On startup, a reconciliation pass re-checks every `uploading` row against S3 (HEAD) and resolves it to `uploaded` (transfer actually completed) or `pending` (retry), before normal processing resumes. No row is ever silently left ambiguous.
- **Content-hash dedup** (sha256): because Takeout re-exports the same photo once per album, the same content is frequently discovered under multiple zip-entry paths. Only the first occurrence is uploaded; subsequent occurrences are recorded as `skipped_duplicate` pointing at the canonical S3 key, and reported to the user as bytes saved. This is a direct cost-reduction mechanism (Glacier IR bills per GB) and is default-on for this tool, per the business goal.

## 5. Credentials & first-run UX (open-source distribution constraint)

The tool must be usable by non-technical third parties with zero prior AWS tooling experience (explicit requirement). Per the user's explicit choice, an **interactive setup wizard always runs** on first use (or on `--reconfigure`) rather than silently depending on ambient AWS env vars/`~/.aws/credentials`. To avoid inventing a bespoke secret store (a real security smell for a distributable OSS tool whose source anyone can read), the wizard **persists the credentials it collects into the standard `~/.aws/credentials` file**, under a dedicated named profile (default `gphotos2s3`), with the file constrained to owner-only permissions (`0600`) after writing. This keeps secret handling inside the exact mechanism every other AWS CLI/SDK tool and every credential-hygiene scanner already knows to look for, while still satisfying "always ask, don't assume" for the target non-technical audience. Non-secret settings (bucket, prefix, storage class, region, dedupe toggle, local state DB path) live in a separate local `config.json`.

The wizard should also verify the destination bucket exists (or offer to create it privately, `BlockPublicAcls`+friends ON, versioning off by default, with the `AbortIncompleteMultipartUpload` lifecycle rule from §3 attached automatically), and it should print a minimum-privilege example IAM policy (scoped to that one bucket/prefix: `s3:PutObject`, `s3:GetObject`, `s3:ListBucket`, `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts`) so a careful user is not pushed toward over-broad `AdministratorAccess` keys just to get started.

## 6. Testing approach

No real AWS calls or real Google data should ever be needed to develop or verify this tool (and the user explicitly asked that no real upload be executed in this session). `moto` (S3 mocking library for `boto3`) plus small synthetic Takeout-shaped zip fixtures built in test setup give full coverage of discovery, pairing, dedup, upload, resume-after-crash, and verify logic without any live credentials or network access.

## 7. Non-goals confirmed with the user

- No Google Photos API / OAuth integration, no deletion of anything in Google Photos. The tool is strictly one-way, local-files-to-S3. Freeing Google storage remains a manual step the user performs themselves once they trust the backup.
- No execution of an actual upload run in this session — implementation and automated tests only.
